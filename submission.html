Problem Statement

What Problem?

Content creators and developers today waste hours switching between tools — Photoshop for edits, CapCut for cuts, remove.bg for background removal, Canva for social exports, and separate AI tools for generation. There is no single browser-based platform that unifies AI-powered image editing (background removal, smart crop, transformations), video processing (compression, timeline editing, clip arrangement), and AI generation (image/video/animation) in one authenticated, per-user workspace.

The vision is a complete AI media workplace:

Phase 1 — Now Core image transformations using Cloudinary's API — background removal, smart crop for social formats, filters, enhancements — making it a genuinely usable image editor in the browser.
Phase 2 A drag-and-drop timeline editor where users arrange image/video clips, with server-side export via FFmpeg — enabling short-form video creation (Reels, Shorts).
Phase 3 Integration of AI generation models (image-to-video, animation, text-to-video) to complete the end-to-end AI media pipeline.

Why This Problem?

In the current AI video-making era, short-form content (30-second Reels, YouTube Shorts) is the dominant format. If a platform can combine Cloudinary's transformation API with AI generation models for that last-mile video output — actual clip rendering with transitions, effects, and AI-generated segments — it becomes a genuinely useful tool for creators who don't have the budget for Adobe or the technical skill to stitch together multiple APIs themselves. Starting with image hero-features first ensures the foundation is solid before the timeline and generation layers are added on top.

Approach & Thought Process

Idea Workflow

Feature Decision → Design → Break into subtasks → Implement with Claude Code → Test → Debug → Deploy

Feature Prioritization Order

The stack was validated early with video upload and compression — this proved the Cloudinary integration, DB pipeline, and per-user auth worked end-to-end. After that, priority deliberately shifted to the image pipeline. The reasoning: image transformations are stateless, faster to ship, and easier to test. Completing the image hero-features first also means the playground UI and editor shell are mature before the timeline feature is introduced — so the timeline can be tested against real, already-working tools rather than being built in isolation.

  • Core infra (auth, DB, Cloudinary, file upload)
  • Video upload + compression (stack validation)
  • Image pipeline — crop, bg-remove, transformations (hero features, foundation for timeline)
  • Timeline editor — drag-and-drop clip arrangement, FFmpeg server-side export
  • AI generation models — image/video generation, animation

What Made the Approach Unique

Claude Code was used as an autonomous agent, not autocomplete. But more importantly, the developer workflow around it was deliberate:

  1. Design before implementation. Before writing a single line, the full feature pipeline was designed — what the data flow looks like, which files need to be created vs. updated, what the folder structure should be, how the API route connects to the component, where shared logic lives.
  2. Confirm the plan, then implement. Claude Code was asked to plan first — list the files, describe what each does, explain the data flow. Only after reviewing and approving that plan was it given the green light to implement. This prevents AI agents from drifting from the intended architecture.
  3. Post-implementation review. After every feature, the generated code was reviewed against the original design: Did the API route follow the established auth pattern? Did shared constants end up in the right place? Did the component structure match what was designed?
Design → Approve → Implement → Review — The agent handles execution. The developer owns the architecture.

Build Explanation

Each feature follows the same vertical slice pattern — API route → service layer → component → page integration. The API handles auth and calls Cloudinary. The component handles UI state and calls the API. Everything typed, everything per-user.

App Restructuring for Future Scope

Before implementing new features, the app architecture was deliberately restructured with future scope in mind. The early version had features loosely tied to pages — no shared shell, no common dashboard, tools scattered across routes. That doesn't scale when the roadmap includes a timeline editor, AI generation tools, and multi-format exports.

Redesigned Structure
  • A common dashboard that will eventually surface all media (images, videos, generated clips) in one place
  • A unified editor shell (EditorShell.tsx) that all tools (crop, bg-remove, future transformations) load into — shared image state, shared loading skeleton, shared layout
  • A playground route (/playground/[id]) that acts as the container, keeping tool-switching stateful

This means when the timeline editor is added, it slots into an already-mature shell rather than requiring a second full restructure. The restructuring cost is paid once now, not repeatedly later.

Implementation with Claude Code

This is where the agentic workflow shows its value most clearly. For each feature, the flow was:

  1. Design the pipeline — data flow mapped out before any code: which files get created, which get updated, what each layer's responsibility is.
  2. Claude Code plans first — asked to list files and describe what each does before writing anything.
  3. Approve the plan — review the proposed structure against the design, confirm it matches.
  4. Claude Code implements — writes across all files in one session: API route, service, component, types, page integration.
  5. Review against design — check auth pattern, shared constants placement, import comments per CLAUDE.md, component structure.

What Claude Code does well here: it reads existing files before writing new ones, recognises established patterns, and applies them consistently without being told. CLAUDE.md acts as a permanent rulebook — read at the start of every session, so architectural rules are enforced automatically without re-explaining them each time.

Key Features

Clerk + DB Sync

Clerk handles authentication out of the box. But the platform needs a DB user row to store per-user media. This is solved via a Clerk webhook — when a user signs up, Clerk fires a user.created event to /api/webhooks/clerk, which creates the corresponding DB record. All subsequent API routes look up the DB user by clerkId. The onboarding gate in middleware checks publicMetadata.onboardingComplete so no DB call is needed at the Edge.

Background Removal

Cloudinary has a built-in AI transformation: e_background_removal. Instead of calling an external ML API, the image's Cloudinary public ID is passed to a transformation URL. Cloudinary processes it server-side and returns a PNG with the background removed. No model hosting, no extra cost per call beyond the Cloudinary plan.

Smart Crop for Social Formats

Cropping is done via Cloudinary's URL-based transformation API — c_fill, w_{width}, h_{height}, g_auto (AI-powered gravity that detects the subject and centers it). The user picks a social format preset (Instagram 1:1, Twitter 16:9, Facebook Cover, etc.), and the transformed URL is generated instantly. No server processing — just a URL parameter change, and Cloudinary handles the rest on delivery.

Why This Matters
🔁
The Meta-Layer Is the Story

The platform processes media with AI, and it was built with an AI agent. This demonstrates that agentic workflows are not hype — they are a practical, repeatable development methodology that a solo developer can apply to ship real products.

📋
CLAUDE.md as a Team Rulebook

A living specification file was maintained that Claude Code reads before every session. This is equivalent to onboarding a new developer with a style guide — except the agent follows it perfectly every time. Constants go in lib/constants/. Shared singletons go in lib/. Imports have comments explaining why they're shared. This discipline enforced by a file, not by repetition, is what keeps a solo-built codebase clean at scale.

🧠
Memory Across Sessions

Claude Code maintained project memory across multiple conversations — architecture, DB schema, coding patterns, known issues. There was no need to re-explain the stack at the start of each session. This is how agentic tools enable a solo developer to maintain the mental overhead of a much larger codebase.

⚡
Speed with Correct Architecture

Features that would take a solo developer days — bg-remove with API route, service layer, component, types, and playground integration — were shipped in hours, with the right structure from the start. Not prototype-quality code patched together. Production-ready, consistently patterned code that fits the existing architecture.
